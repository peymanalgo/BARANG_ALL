# 1. خلاصه مدیریتی پروژه

BARANG سامانه‌ای برای مدیریت سفارش‌ها و فرایندهای کسب‌وکار چاپ پوشاک است که باید به‌صورت یک محصول کامل و قابل توسعه ساخته شود. معماری محصول شامل **یک پایگاه داده مشترک و سه برنامه کاربردی** است:

1. **Core / Backoffice:** سامانه داخلی کارکنان برای مدیریت سفارش‌ها و عملیات کسب‌وکار؛ باید ابتدا به‌صورت مستقل و کامل قابل استفاده شود، از جمله ثبت سفارش حضوری توسط کارکنان.
2. **B2C Web App:** وب‌سایت مشتریان.
3. **Customer Mobile App:** برنامه موبایل مشتریان.

اولویت اصلی در انتخاب فناوری، **سرعت و قابلیت اتکای تولید با کمک Codex** است؛ در عین حال، ساختار باید تمیز، قابل آزمون، امن، قابل نگهداری و قابل توسعه باشد.

## اصول غیرقابل مذاکره

- تغییر دامنه یا افزودن قابلیت خارج از درخواست و اسناد مبنا ممنوع است.
- کارها مرحله‌به‌مرحله انجام شوند؛ هر مرحله باید معیار پذیرش و اعتبارسنجی داشته باشد.
- اسناد تحلیل کسب‌وکار و معماری، مبنای نیازمندی‌ها هستند؛ فناوری‌های قدیمی احتمالی در اسناد نباید بدون بازبینی به طراحی جدید منتقل شوند.
- در پیاده‌سازی BARANG، از فناوری‌ها و اصطلاحات فنی ممنوع‌شده در دستورهای پروژه استفاده نشود؛ پشته مصوب در این سند ملاک است.
- تمام رابط‌های کاربری باید از فارسی، انگلیسی و عربی پشتیبانی کنند.
- پس از هر فاز، آزمون‌ها و اعتبارسنجی‌ها باید انجام شوند؛ صرفاً سبز بودن build کافی نیست.
- سرویس‌های Docker پس از پایان کار باید در صورت نیاز روشن و قابل دسترسی باقی بمانند؛ داده‌ها و volumeها حفظ شوند.
- عملیات Git باید محدود، شفاف و مطابق قواعد این سند باشد.
- UI/UX بسیار مهم است و خروجی نباید صرفاً از نظر فنی کار کند؛ باید مدرن، منسجم و قابل استفاده باشد.

- **.NET 10**
- **ASP.NET Core**
- **PostgreSQL**

- کاربر ترجیح می‌دهد زیرساخت محلی قابل اجرا باشد و برای راه‌اندازی روزمره تا جای ممکن به Docker Hub متکی نباشد؛ پیش از انتخاب image یا dependency، امکان دسترسی و جایگزین عملی بررسی شود.
- انتخاب فناوری جدید یا تغییر پشته بدون ضرورت مستند و تأیید کاربر انجام نشود.

# 4. معماری کسب‌وکار و محصول

## 4.1 سه برنامه، یک پایگاه داده

هر سه برنامه به یک پایگاه داده مشترک متصل می‌شوند، اما نقش‌ها و تجربه کاربری آن‌ها متفاوت است:

- کارکنان از Backoffice/Core برای مدیریت سفارش و عملیات استفاده می‌کنند.
- مشتریان از وب‌سایت B2C و اپ موبایل استفاده می‌کنند.
- Backoffice باید پیش از توسعه کامل B2C و موبایل، به‌عنوان محصول داخلی مستقل و قابل استفاده تکمیل شود.

## 4.2 فرایند و محاسبه سفارش

اسناد اولیه کسب‌وکار مربوط به سامانه سفارش چاپ تی‌شرت هستند. فرمول قیمت سفارش که در مبنای کسب‌وکار آمده است:

**قیمت نهایی = قیمت خام تی‌شرت + چاپ جلو + چاپ پشت + چاپ اضافه + بسته‌بندی + ارسال − تخفیف + مالیات**

این فرمول باید با اسناد جاری تحلیل کسب‌وکار تطبیق داده شود و نباید بدون بررسی، قواعد مالی جدیدی به آن اضافه شود.

## 4.3 گردش‌کار

- فرایند کسب‌وکار دارای جریان مشخص است و فقط بخش‌هایی که در اسناد به‌عنوان قابل تنظیم تعریف شده‌اند باید قابل پیکربندی باشند.
- Elsa Workflows برای گردش‌کارهای موردنیاز در نظر گرفته شده است.
- Hangfire برای اجرای کارهای پس‌زمینه و زمان‌بندی‌شده در نظر گرفته شده است.
- جزئیات اجرایی هر فرایند باید از اسناد تحلیل و معماری استخراج و با تست پوشش داده شود؛ فرض یا قابلیت جدید نباید جایگزین نیازمندی مستند شود.

# 5. الزامات عمومی و دائمی

## 5.1 چندزبانه بودن و جهت نمایش

تمام UIهای BARANG، از جمله صفحه ورود، Backoffice/Core، پیام‌ها، منوها، فرم‌ها، گریدها، selectorها، اعتبارسنجی‌ها و صفحات آینده باید از این زبان‌ها پشتیبانی کنند:

| زبان | کد | جهت |
|---|---|---|
| فارسی | `fa` | RTL |
| انگلیسی | `en` | LTR |
| عربی | `ar` | RTL |

الزامات:

- تغییر زبان در زمان اجرا ممکن باشد.
- زبان انتخابی فقط عنوان منوها را تغییر ندهد؛ پیام‌های خطا، validation، متن دکمه‌ها، وضعیت‌ها، تاریخ‌ها و تمام UI را پوشش دهد.
- جهت RTL/LTR باید به‌صورت سراسری و درست اعمال شود.
- شناسه‌ها، نام کلاس‌ها، نام APIها، نام فیلدهای فنی، نام پروژه‌ها و سایر شناسه‌های فنی انگلیسی باقی بمانند.
- متن‌ها و resourceهای ترجمه‌شده باید منظم، کامل و قابل نگهداری باشند؛ از متن‌های پراکنده و hard-code شده پرهیز شود.
- زبان و جهت در صفحه ورود نیز باید درست عمل کنند.

## 5.2 استاندارد تاریخ

یک موتور تاریخ متمرکز و استاندارد برای کل سامانه لازم است:

- در رابط فارسی (`fa`)، تاریخ‌ها باید شمسی/جلالی نمایش داده و دریافت شوند.
- در رابط انگلیسی (`en`) و عربی (`ar`)، تاریخ‌ها به‌صورت میلادی نمایش داده و دریافت شوند، مگر آنکه کاربر بعداً صریحاً تصمیم دیگری بگیرد.
- ذخیره‌سازی باید مستقل از locale و با قالب canonical باشد؛ زبان رابط نباید مقدار ذخیره‌شده را تغییر دهد.
- تبدیل رفت‌وبرگشت بین تقویم نمایشی و مقدار canonical باید قابل اعتماد باشد.
- این قاعده برای تمام فیلدهای تاریخ، از جمله تاریخ تولد (Birth Date)، تاریخ اسناد، قراردادها، انقضاها و فیلدهای آینده اعمال شود.
- از پیاده‌سازی جداگانه و ناسازگار تبدیل تاریخ در هر صفحه خودداری شود.

## 5.3 استاندارد UI/UX

کیفیت UI/UX برای کاربر اهمیت بسیار زیادی دارد. طراحی باید:

- مدرن، حرفه‌ای، منسجم و مناسب نرم‌افزار عملیاتی سازمانی باشد.
- منوها، آیکون‌ها، گریدها، فرم‌ها، selectorها، صفحات master-detail و جزئیات رکوردها با دقت طراحی شوند.
- سلسله‌مراتب بصری، فاصله‌گذاری، وضعیت بارگذاری، حالت خالی، خطا، موفقیت و تأیید عملیات روشن باشد.
- RTL/LTR و نمایش متن‌های ترکیبی را درست پشتیبانی کند.
- در همه صفحات از یک سیستم طراحی مشترک پیروی کند.
- آیکون‌ها معنای درست داشته باشند؛ برای مثال آیکون افزودن زیرگروه/زیرشاخه دسته‌بندی نباید شبیه آیکون شخص باشد و باید از نماد مرتبط با دسته‌بندی/پوشه/درخت استفاده کند.
- استاندارد دائمی UI/UX در مسیر `D:\00_BARANG\04_Document\01_UI_UX\BARANG_BACKOFFICE_UI_UX_STANDARD.md` نگهداری و در کارهای Codex رعایت شود.

# 6. قواعد Git و تحویل کار

## 6.1 اصول عمومی

- مخزن واحد Git برای پروژه استفاده شود.
- `main` نمایانگر وضعیت اعتبارسنجی‌شده باشد.
- از commitهای کوچک، اتمیک و با قالب Conventional Commits و scope مرتبط با BARANG استفاده شود.
- از push یا ایجاد tag خودکار و بدون درخواست/اجازه خودداری شود، مگر آنکه دستور جاری کاربر صریحاً خواسته باشد پس از اعتبارسنجی push انجام شود.
- از GitFlow و branchهای پیچیده بدون نیاز واقعی استفاده نشود.
- `force-push`، reset مخرب، حذف داده، پاک‌سازی گسترده یا هر عملیات برگشت‌ناپذیر بدون اجازه صریح ممنوع است.
- پیش از commit، تست‌ها و اعتبارسنجی‌های لازم باید موفق باشند.
- فقط فایل‌های متعلق به فاز جاری stage شوند؛ فایل‌های نامرتبط، فایل‌های کاربر و `04_Document` را بدون اجازه دست‌کاری یا stage نکنید.
- پس از پایان، گزارش دقیق از فایل‌های تغییرکرده، تست‌ها، commit و push ارائه شود.

## 6.2 روند تحویل هر فاز

1. بررسی مخزن، اسناد، کد، تنظیمات و وضعیت سرویس‌ها.
2. تعیین محدوده دقیق و معیارهای پذیرش.
3. اجرای فقط کار مربوط به فاز جاری.
4. اجرای build، تست‌های واحد، یکپارچه‌سازی، UI/E2E و بررسی‌های امنیتی مرتبط.
5. اجرای تست‌های مرورگر و بررسی واقعی سناریوهای کاربر، هرجا لازم است.
6. بررسی migration و سلامت پایگاه داده.
7. بررسی زبان‌های `fa/en/ar`، RTL/LTR و تاریخ‌ها.
8. بررسی لاگ‌ها، health endpointها و سلامت سرویس‌ها.
9. بررسی diff و اطمینان از نبود تغییر ناخواسته.
10. commit فقط پس از موفقیت اعتبارسنجی و مطابق دستور جاری.
11. push پس از اعتبارسنجی، در صورتی که طبق دستور جاری کاربر لازم باشد.
12. نگه داشتن سرویس‌های Docker موردنیاز روشن و ارائه گزارش نهایی.

## 6.3 نام‌گذاری commit

نمونه‌های ثبت‌شده:

- `docs(core): define git workflow`
- `docs(core): define naming conventions`
- `chore(core): bootstrap .NET 10 Docker foundation`
- یک دستور تاریخی برای فاز context شرکت: `feat(core): complete authenticated company context`

قالب کلی پیشنهادی: `<type>(<scope>): <short description>`. نام scope باید با بخش واقعی پروژه هماهنگ باشد.

# 7. Docker، اجرا و سلامت سرویس‌ها

## 7.1 قواعد اجرایی

- Docker Desktop و Docker Compose بخش اصلی گردش‌کار توسعه محلی هستند.
- پس از پایان هر فاز، سرویس‌های لازم باید روشن و از طریق browser/API/Docker Desktop قابل بررسی باشند.
- **از `docker compose down` استفاده نشود** مگر کاربر صریحاً درخواست کرده باشد یا پاک‌سازی واقعاً ضروری و تأیید شده باشد.
- volumeهای نام‌دار و داده‌های موجود حفظ شوند.
- پیش از تغییر compose یا migration، اثر آن بر داده‌های محلی بررسی شود.
- سلامت سرویس‌ها فقط از روی خروجی build نتیجه‌گیری نشود؛ health check، API، پایگاه داده و رابط کاربری نیز بررسی شوند.

## 7.2 وضعیت‌های تاریخی محیط

در گزارش‌های قبلی این موارد ثبت شده‌اند؛ وضعیت فعلی باید هنگام ادامه کار دوباره بررسی شود:

- نسخه‌های گزارش‌شده در یک مقطع: `.NET SDK 10.0.400`، Git `2.55.0`، Docker `29.6.1`، Docker Compose `v5.3.0`، PowerShell `7.6.5` و Codex CLI `0.149.1`.
- Docker Desktop روی محیط `desktop-linux` اجرا شده بود.
- PostgreSQL نسخه `17.6` و Core API در یک مقطع سالم گزارش شده بودند.
- آدرس‌های محلی گزارش‌شده: `127.0.0.1:5432` برای PostgreSQL و `http://localhost:8080` برای Core API.
- در مقطعی `docker ps` هیچ container فعالی نشان نمی‌داد؛ بنابراین گزارش‌های سلامت تاریخی را نباید وضعیت فعلی فرض کرد.
- در یک مرحله اعتبارسنجی به دلیل مجوز named pipe متوقف شده بود؛ در آن گزارش فایل‌ها stage یا commit نشده بودند.

# 11. قواعد تهیه Prompt برای Codex

Promptهای Codex باید:

- تا حد ممکن کوتاه و کم‌توکن باشند، اما تمام محدودیت‌ها و معیارهای لازم را حفظ کنند.
- انگلیسی باشند، مگر آنکه کاربر زبان دیگری بخواهد.
- دقیقاً محدوده و هدف یک فاز را مشخص کنند.
- پیش از تغییر، بررسی اسناد، کد، ساختار repo، وضعیت Git و runtime را الزام کنند.
- به Codex بگویند از تغییرات خارج از scope خودداری کند.
- الزامات `fa/en/ar`، RTL/LTR و تاریخ را برای UI و فیلدهای مرتبط فراموش نکنند.
- معیارهای پذیرش و تست‌های لازم را مشخص کنند.
- build، unit tests، integration tests، browser/E2E، migration، API health و UI واقعی را در صورت ارتباط مطالبه کنند.
- از commit/push/tag خودکار اجتناب کنند مگر دستور همان مرحله صریحاً آن را مجاز کرده باشد.
- Docker Compose را در حالت قابل استفاده حفظ کنند و `docker compose down` اجرا نکنند.
- در پایان، گزارش کوتاه و مستند شامل تغییرات، تست‌ها، مشکلات باقی‌مانده، وضعیت سرویس‌ها و وضعیت Git ارائه کنند.
- از بازنویسی کل سیستم یا refactor گسترده خارج از درخواست جلوگیری کنند.
- هرگونه نیازمندی مبهم را از اسناد موجود استخراج کنند؛ اگر واقعاً مسدودکننده است، سؤال مشخص مطرح کنند و فرض پنهانی نسازند.

## الگوی منطقی یک Prompt

1. **Audit first:** repo، اسناد، کد، تست‌ها، runtime و Git را بررسی کن.
2. **Scope:** فقط کار مشخص‌شده را انجام بده.
3. **Constraints:** زبان‌ها، تاریخ، امنیت، company scope، Docker و Git را رعایت کن.
4. **Implementation:** تغییرات کامل را در لایه‌های مرتبط پیاده کن.
5. **Validation:** تست‌های مربوط و مرورگر را اجرا کن.
6. **Report:** نتیجه واقعی، تست‌های اجراشده، موانع و وضعیت Git/runtime را گزارش کن.
7. **No false completion:** قابلیت ناقص را کامل اعلام نکن.

1. وضعیت واقعی GitHub و local repository و اینکه کدام commitها push شده‌اند.
2. وضعیت فعلی سرویس‌های Docker و سلامت Core API/PostgreSQL/Redis/MinIO.
3. وضعیت دقیق فازهای اولیه و company context.
4. وضعیت جاری Supplier و رفع چهار مانع اصلی Prompt 4.
5. وضعیت اجرای Prompt 5 و یکپارچه‌سازی داده‌های پایه مشترک.
6. وجود و محتوای سند استاندارد UI/UX در مسیر تعیین‌شده.
7. تطبیق Backoffice با تمام نیازمندی‌های Business Analysis و Software Architecture.
8. آماده‌بودن انتقال Backoffice به `01_CORE` پس از پذیرش نهایی.
9. اطمینان از اینکه `02_WEB_APP` پس از refactor فقط برای B2C استفاده شود.
10. بررسی کامل localization، تاریخ شمسی/میلادی، RTL/LTR، امنیت، company scope و تست‌های مرورگر.

# 19. اصل نهایی پروژه

**BARANG زمانی آماده تحویل است که قابلیت‌ها نه‌فقط کدنویسی، بلکه بر اساس اسناد، آزمون‌های خودکار، سناریوهای واقعی UI، امنیت، داده‌ها، زبان‌ها، تاریخ‌ها و سلامت اجرا اعتبارسنجی شده باشند.**

در هر مرحله، وضعیت واقعی از حدس و گزارش تاریخی مهم‌تر است. هیچ کار ناقصی نباید کامل اعلام شود؛ هیچ تغییر خارج از دامنه نباید بی‌اجازه انجام شود؛ و هیچ داده یا فایل کاربر نباید با عملیات ناخواسته Git یا Docker در معرض خطر قرار گیرد.
